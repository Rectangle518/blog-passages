## 1. 总体思路

由于我对 Golang 也有点忘了，我在一开始看到代码的时候完全不知道该怎么入手，只是先看了一下示例的 RPC 调用。借助 AI 的解释，我看懂之后，就又让 AI 给我提供第一步的实现思路。

先实现 Map 操作，先不管 Reduce 操作。所以这就导致，我的代码里，把 Map 和 Reduce 分开了，出现了很多冗余重复的代码，复用性很差。

下面简单介绍一下整体思路。

整体上，一个作业分成 Map 和 Reduce 两个阶段。Coordinator 启动时会给每个输入文件建一个 Map 任务，再根据传进来的 `nReduce` 建一组 Reduce 任务。Worker 启动后就通过 RPC 向 Coordinator 要任务，领到任务就执行，执行完上报，然后再领下一个。如果暂时没有任务可领，就等一秒再问。

Map 阶段，Worker 先读完输入文件，再调用插件里的 `Map` 函数。拿到中间键值对之后，用 `ihash(key) % nReduce` 决定每条记录写到哪个分区。这样，同一个 key 即使出现在不同的输入文件里，也会被分到同一个 Reduce 任务。比如每个 Map 写出来的 2 号分区，最后都由 Reduce 任务 2 来读。

Coordinator 收到所有 Map 的完成上报后，才开始分配 Reduce 任务。一个 Reduce 任务会把各个 Map 写给自己的分区都读进来，合在一起按 key 排序。这样相同的 key 就挨在一起了，可以把它们的 value 一次交给 `Reduce` 函数，结果写到对应的 `mr-out-X` 文件。等所有 Reduce 都上报完成，`Done()` 就会返回 `true`，Coordinator 随后退出。

## 2. 一些细节处理

### 2.1 Coordinator 不知道 Worker

我借鉴了 @OneSizeFitsQuorum 的思路，让每个 Worker 是无状态的，也就是说，Coordinator 实际上不知道有哪些 Worker 存在。Coordinator 只接受 RPC 请求，然后分配任务，它并不知道这个任务分配给了哪个 Worker。

因此，我也没有实现所谓的心跳机制来检测 Worker 是否挂了，因为在这个设计中，Coordinator 实际上并不需要知道 Worker 的状态。

那如果有任务挂了怎么办，答案是超时机制。这里的设计是，只有在有 RPC 请求到来时，Coordinator 才会遍历所有任务，找到一个处于 Idle 状态的任务，或者找到一个处于 Running 状态但已经超时的任务，然后分配任务即可。当没有 RPC 请求到来时，Coordinator 不会做任何事情。这里实际上要求每个活着的 Worker 一定要定期向 Coordinator 发送 RPC 请求，否则任务就无法分配了。

### 2.2 文件写入

任务可能会触发超时重试。但实际上，超时并不一定意味着任务挂了，也可能只是一个 Worker 执行的很慢，也可能是网络延迟。而触发超时重试之后，Coordinator 会把这个超时的任务重新发射一次，因此可能有两个甚至多个 Worker 在同时执行同一个任务。

在 Lab1 中，文件的写入方式与实际的 MapReduce 是不同的。在 Lab1 中，由于只有一台机器，每个 Worker 会把每个 Map 和 Reduce 的所有结果写入到本地同一个目录下，需要处理一下文件名冲突的问题。假设有两个 Worker 在执行同一个任务，那么它们会同时写入一个同名文件，这就有问题了。这里的处理方式是，给一个任务的每一次执行都分配一个 AttemptId 来唯一标识此次尝试执行的任务，这样，每个 Worker 在写入文件时，都会在文件名中加上 AttemptId，这样就可以避免文件名冲突的问题。

当 Worker 执行完一个任务之后，会向 Coordinator 发送一个 RPC 请求进行任务提交，告知 Coordinator 任务已经完成。Coordinator 会进行检查，检查这个任务是否已经被标记为 Completed，防止重复提交同一个任务。如果这个任务是第一次被提交，Coordinator 会返回一个 true，当 Worker 收到这个 true 之后，就会进行文件重命名，把 AttemptId 去掉，变成最终的文件名，效果上相当于正式发布这个结果文件。反之，如果这不是该任务的第一次提交，Coordinator 会返回一个 false，当 Worker 收到 false 时，不会进行重命名。

这里其实有一个小问题没有解决，如果 Worker 在收到 true 之后，在重命名之前挂了，那么这个任务的结果文件就不会被发布，但是 Coordinator 已经将这个任务标记为 Completed，这会导致 Coordinator 认为这个任务已经完成，不会再重试这个任务。

还有一个情况，如果现在执行的是最后一个 Map 任务，Coordinator 一将这个任务标记为 Completed，Worker 就可以开始执行 Reduce 任务，而此时，最后这个 Map 任务的结果文件可能还没有被重命名，Reduce 任务可能读不到这个文件。但这个问题不大，因为 Reduce 任务如果发现读不到文件就会直接返回，然后 Coordinator 会在超时之后会重新执行这个 Reduce 任务。同样的，这里 Reduce 任务的结果文件也采用了同样的重命名和发布机制，但如果是最后一个 Reduce 任务，那么 Coordinator 进程就可能在最后一个 Reduce 任务的结果文件发布之前就退出了，这会导致最后一个 Reduce 任务的结果文件没有被发布。
