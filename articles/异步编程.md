
不同编程语言之间的区别远不止语法，异步编程机制的差异正是一个绝佳的例证。

## JavaScript异步编程

JavaScript 是一门**单线程**语言，这意味着同一时间只能执行一个任务。如果所有代码都同步执行，遇到网络请求、文件读取或定时器等耗时操作时，整个页面就会卡死，无法响应用户的任何操作。

为了解决这个问题，JavaScript 引入了**异步编程**模型。它允许主线程在等待耗时操作完成的同时，继续执行后面的代码，等异步操作有了结果，再通过回调机制通知主线程去处理。

JavaScript 的异步编程主要经历了以下三个阶段的演进：

### 1. 回调函数 —— 最原始的方式
在早期的 JS 中，我们通过将一个函数作为参数传递给另一个函数，等异步操作完成后，再调用这个函数（即回调）。
*   **优点**：简单直接。
*   **缺点**：当多个异步操作存在依赖关系（比如：先获取用户信息，再根据用户ID获取订单，再根据订单获取商品详情）时，回调函数会一层套一层，形成臭名昭著的**“回调地狱”（Callback Hell）**。这导致代码可读性极差，且错误处理非常繁琐。

### 2. Promise —— 解决回调嵌套
ES6 引入了 Promise，它是一个代表异步操作最终完成（或失败）及其结果值的对象。Promise 有三种状态：`pending`（等待中）、`fulfilled`（成功）、`rejected`（失败）。

*   **优点**：
    *   **链式调用**：通过 `.then()` 将嵌套的回调变成了扁平的链式结构，代码逻辑更清晰。
    *   **统一错误处理**：可以通过 `.catch()` 统一捕获前面链路上所有的错误。
*   **缺点**：虽然解决了嵌套问题，但大量的 `.then()` 链式调用依然会让代码显得冗余，不够直观。

### 3. Async / Await —— 现代异步编程
ES2017 引入的 `async/await` 是基于 Promise 的语法糖。它允许你用**写同步代码的方式去写异步逻辑**，是目前前端和 Node.js 开发的主流标准。

*   **核心用法**：
    *   `async`：声明一个函数是异步的，该函数会默认返回一个 Promise。
    *   `await`：只能在 `async` 函数内部使用，用于“等待”一个 Promise 返回结果。它会暂停当前函数的执行，但**不会阻塞 JS 主线程**。
*   **优点**：代码极其简洁优雅，并且可以直接使用 `try/catch` 来捕获异步错误，调试体验也非常好。

**三者代码直观对比：**

```javascript
// 1. 回调地狱 (Callback Hell)
getUser(function(user) {
  getPosts(user.id, function(posts) {
    getComments(posts[0].id, function(comments) {
      console.log(user, posts, comments);
    });
  });
});

// 2. Promise 链式调用
getUser()
  .then(user => getPosts(user.id))
  .then(posts => getComments(posts[0].id))
  .then(comments => console.log(comments))
  .catch(err => console.error(err));

// 3. Async / Await (现代最清晰)
async function getData() {
  try {
    const user = await getUser();
    const posts = await getPosts(user.id);
    const comments = await getComments(posts[0].id);
    console.log(user, posts, comments);
  } catch (err) {
    console.error(err);
  }
}
```

### 底层机制：事件循环 (Event Loop)
理解异步编程，必须了解它的底层调度机制——**事件循环**。JS 引擎通过事件循环来协调同步代码和异步任务的执行顺序。

事件循环将异步任务分为两类队列：
*   **宏任务 (MacroTask)**：优先级较低。常见的有 `setTimeout`、`setInterval`、I/O 操作、UI 渲染等。
*   **微任务 (MicroTask)**：优先级较高。常见的有 `Promise.then/catch/finally`、`async/await`（await 后面的代码会被包装成微任务）。

**事件循环的经典执行顺序：**
1. 执行完当前所有的**同步代码**（属于第一个宏任务）。
2. 立刻清空**所有**的微任务队列。
3. 从宏任务队列中取出**一个**宏任务执行。
4. 重复步骤 2 和 3，不断循环。

**看个经典的执行顺序例子：**
```javascript
console.log('1. 同步代码开始');

setTimeout(() => {
  console.log('2. 宏任务 (setTimeout)');
}, 0);

Promise.resolve().then(() => {
  console.log('3. 微任务 (Promise.then)');
});

console.log('4. 同步代码结束');

// 最终输出顺序：
// 1. 同步代码开始
// 4. 同步代码结束
// 3. 微任务 (Promise.then)
// 2. 宏任务 (setTimeout)
```

### 进阶技巧：并行执行
在使用 `async/await` 时，如果多个异步任务之间没有依赖关系（比如同时请求用户信息和商品列表），不要逐个 `await`，否则会串行执行拖慢速度。推荐结合 `Promise.all` 来并行执行：

```javascript
// ❌ 串行执行，总耗时 = 任务1 + 任务2
const user = await fetchUser();
const products = await fetchProducts();

// ✅ 并行执行，总耗时 = 耗时最长的那个任务
const [user, products] = await Promise.all([
  fetchUser(),
  fetchProducts()
]);
```

掌握从回调到 `async/await` 的演进，并理解事件循环的底层原理，是写出高效、优雅 JavaScript 代码的必经之路。


## Python异步编程

### 1. 一段代码示例

```python
import time
import asyncio

async def task1():
    await asyncio.sleep(3)
    return 1

async def task2():
    await asyncio.sleep(2)
    return 2

async def main():
    
    event_loop = asyncio.get_running_loop()

    task1_future = event_loop.create_task(task1())
    task2_future = event_loop.create_task(task2())

    result1 = await task1_future
    print("Task 1 result:", result1)
    result2 = await task2_future
    print("Task 2 result:", result2)

    # 也可以这么写，更常用
    # result = await asyncio.gather(task1(), task2())

if __name__ == "__main__":
    start = time.time()
    asyncio.run(main())
    end = time.time()
    print(f"Time taken: {end - start}")
```

### 2. async 关键字

**`async def` 的作用**

`async def` 用于定义异步函数（也叫协程函数），两者在当前语境下是等价的概念。协程函数能够执行非阻塞操作，并在等待某些任务完成时，允许程序切换到其他任务执行，待合适时机再恢复原任务的执行。例如，当 task1 执行到 `await asyncio.sleep(5)` 时，不会阻塞等待5秒，而是立即切换到 task2 去执行，等 task2 完成后再回来继续 task1。

**协程函数的调用与普通函数的区别**

普通函数（用 `def` 定义）调用时会直接执行函数体；而协程函数（用 `async def` 定义）调用时**不会直接执行函数体**，而是返回一个**协程对象（coroutine object）**。通过 `type()` 检查可以发现其类型为 `coroutine`。

**协程对象的理解**

协程对象本质上是一个**未开始执行的任务**。因为协程函数的设计初衷就是交给事件循环（Event Loop）去调度执行，所以调用时不会立即执行，而是延迟到事件循环中。要真正执行协程对象，需要使用 `asyncio.run()` 方法——它会创建事件循环、将协程对象注册进去，然后由事件循环自动调度执行。

**为什么异步编程必须使用协程而非普通函数**

核心原因在于：普通函数一旦调用就会从头执行到尾，**不支持暂停和恢复**；而协程对象由 Python 底层支持，能够在执行过程中**挂起（暂停）和恢复**。在异步编程中，任务遇到 `await` 时需要挂起，让出执行权给其他任务，等待完成后再恢复执行——这种"暂停-恢复"机制只有协程才能实现，普通函数无法做到。

**小结**

| 要点 | 说明 |
|------|------|
| `async def` | 定义异步/协程函数 |
| 调用协程函数 | 返回协程对象，不直接执行函数体 |
| 协程对象 | 未开始执行的任务，需交由事件循环调度 |
| 事件循环执行 | 通过 `asyncio.run()` 创建并运行 |
| 协程 vs 普通函数 | 协程支持暂停和恢复，普通函数不支持 |

### 3. await 关键字

**`await` 的基本作用**

`await` 只能用在 `async def` 定义的协程函数中，其作用是暂停当前协程的执行，直到后面的异步操作完成后再恢复执行后续代码。例如 task1 执行到 `await` 时会挂起，等异步操作完成后再继续向下执行。

**`await` 后面可以跟的三种对象**

| 对象类型 | 行为 |
|---------|------|
| **Task 对象** | 事件循环直接去执行该任务 |
| **协程对象（coroutine）** | 事件循环直接去执行该协程函数，**不会切换到其他任务** |
| **Future 对象** | 事件循环会**挂起当前任务，切换到其他任务执行** |

如果 `await` 后面跟的不是以上三种类型，Python 会抛出 `TypeError`，提示该对象不能用于 await 表达式。

**`await 协程对象` vs `await Future 对象` 的关键区别**

- **`await 协程对象`**：事件循环会继续执行该协程函数的内容，而**不会**立即切换到其他已注册的任务。整个流程是"串行"的——task1 中 await 一个 sub_task，会先把 sub_task 执行完，再去执行 task2。执行顺序为：task1 → sub_task → task2。

- **`await Future 对象`**：事件循环发现 await 的是一个"未来才会完成的结果"，就会**立即挂起当前任务，切换到其他任务执行**。这才是真正的任务切换时机。执行顺序为：task1 开始 → await future 时挂起 → 切换到 task2 执行 → future 完成后恢复 task1。

**`asyncio.sleep()` 的内部机制与 Future 的桥梁作用**

1. `sleep()` 内部首先通过 `loop.create_future()` 创建一个 Future 对象
2. 然后通过 `loop.call_later()` 注册一个定时器（延迟回调），将真正的等待操作**剥离出事件循环所在线程**，交给系统或其他机制执行
3. Future 对象同时被事件循环和定时器持有——定时器完成后修改 Future 的状态，事件循环通过检查 Future 状态来判断异步操作是否完成
4. 最后 `await` 这个 Future 对象，事件循环发现它是"未来结果"，于是挂起当前任务、切换执行其他任务

**Future 的本质作用**就是事件循环与异步操作之间的**桥梁**——它既让事件循环能感知异步操作的完成状态，又让事件循环在等待期间能腾出手去调度其他任务，从而实现非阻塞的并发执行。

**小结**

`await` 后面跟协程对象时是"直接执行"，跟 Future 对象时才是"切换任务"。`await Future` 是事件循环进行任务切换（上下文切换）的真正时机，而 Future 对象则是连接事件循环与底层异步操作的通信桥梁。


## 一些其他思考

当你在命令行终端输入一个命令来启动程序时，操作系统会为该程序创建一个新的进程。这是操作系统的基本机制，和你启动什么程序无关——无论是 Python 脚本、SpringBoot 服务、还是任何其他可执行程序，都是如此。

> 如果是 `mpirun -n 4 ...` 这种启动方式，会创建多个进程。

### 1. 一个例子

当你在终端输入命令（比如 `java -jar app.jar` 启动 SpringBoot）时，终端（本身就是一个进程，如 bash、zsh、cmd 等）会调用操作系统的 `fork()` + `exec()` 系列系统调用来完成以下操作：

1. **`fork()`**：终端进程创建一个自己的副本（子进程），这个子进程拥有与父进程相同的内存映像、文件描述符等
2. **`exec()`**：子进程用目标程序的代码和数据替换自身，变成一个全新的进程来运行你的程序

所以最终效果就是：终端进程（父进程）+ 新启动的程序进程（子进程），两个进程并存。

### 2. 前台与后台的区别

虽然都是新进程，但运行方式有两种：

| 方式 | 命令示例 | 特点 |
|------|---------|------|
| **前台运行** | `java -jar app.jar` | 终端被占用，等待程序结束后才能输入下一条命令；关闭终端时程序会被终止 |
| **后台运行** | `java -jar app.jar &` | 终端不被占用，可以继续输入其他命令；但关闭终端时程序通常仍会被终止 |

如果你希望程序在关闭终端后继续运行，通常需要额外手段，比如：
- `nohup java -jar app.jar &`：忽略挂断信号，程序不受终端关闭影响
- 使用 `screen` 或 `tmux`：在虚拟终端中运行
- 注册为系统服务（如 systemd）：由操作系统管理生命周期
- Docker 容器化部署：在容器内运行

当执行 `java -jar springboot-app.jar` 时，操作系统的行为是：

1. 终端进程 fork 出一个子进程
2. 子进程 exec 为 `java` 进程
3. JVM 启动后，SpringBoot 应用运行在这个 java 进程中
4. SpringBoot 内部创建的线程（Tomcat 线程池、业务线程等）全部属于这个 java 进程

### 3. 单进程能承载多大并发

不同的并发模型，单进程的承载能力天差地别：

| 并发模型 | 单进程大致承载量 | 典型代表 |
|---------|---------------|---------|
| 同步阻塞（一连接一线程） | 数百\~数千 | 传统 SpringBoot（Tomcat 默认 200 线程） |
| 异步非阻塞（事件驱动） | 数万\~数十万 | Node.js、Nginx、Python asyncio |
| 协程模型 | 数万\~数十万 | Go goroutine、Java 虚拟线程 |

关键区别在于**资源开销**：一个线程栈默认占 1MB 内存，1 万个线程就需要约 10GB，而一个协程只需几 KB，1 万个协程才几十 MB。

### 4. 单进程的真正瓶颈

单进程不够用的原因通常不是"并发量"本身，而是以下三个瓶颈：

**1. CPU 瓶颈——最常见的单进程上限**

一个进程只能跑在一个 CPU 核心上（除非多线程）。如果你的请求需要 CPU 计算（JSON 解析、业务逻辑、数据序列化），单核的处理速度是有物理上限的。假设一个请求的 CPU 时间是 1ms，单核单进程理论上限约 1000 QPS，8 核机器也就 8000 QPS。

对于 CPU 密集型场景，单进程确实不够，必须多进程/多实例来利用多核。

**2. 内存瓶颈**

每个并发连接都需要一定内存来维持状态。同步模型下线程开销大，内存先成为瓶颈；异步/协程模型下内存开销小，这个瓶颈会推迟很多。

**3. I/O 瓶颈**

如果瓶颈是数据库查询慢、下游服务响应慢，单进程的事件循环/线程池照样能处理大量并发连接（因为大部分时间在等 I/O，CPU 空闲），这时单进程反而可能够用。

### 5. 常见的解决方案

#### 方案一：多进程部署（最通用）

无论什么语言、什么框架，最直接的做法就是启动多个进程实例，配合负载均衡：

- **SpringBoot**：同一台机器启动多个 Jar 实例（不同端口），Nginx 做负载均衡；或部署到多台机器
- **Python**：Gunicorn 启动多个 worker 进程，每个 worker 运行一个 asyncio 事件循环
- **Node.js**：PM2 cluster 模式启动多个进程，利用多核

这是最朴素也最可靠的横向扩展方式。

#### 方案二：语言级轻量并发（单进程高并发）

- **Go**：goroutine 极轻量（初始 2KB 栈），单进程可轻松创建数十万 goroutine，且 Go runtime 自带 M:N 调度，自动利用多核。所以 Go 服务单进程就能扛很高并发
- **Java 虚拟线程**（Project Loom，JDK 21+）：类似 goroutine 的轻量线程，SpringBoot 6+ 已支持，单进程并发能力大幅提升
- **Python asyncio**：协程轻量，但受 GIL 限制仍是单核，需要多进程配合

#### 方案三：架构层面拆分

当单机多进程也不够时：
- 微服务拆分，将压力分散到不同服务
- 读写分离、缓存层（Redis）减轻后端压力
- 消息队列异步化，削峰填谷
- CDN、边缘计算分担流量

### 6. 回到原本场景

如果你用 SpringBoot 做后端：

- **传统模式**（平台线程）：Tomcat 默认 200 线程，单进程能扛几百并发。要扛更多，需要多实例部署
- **虚拟线程模式**（JDK 21+ SpringBoot 3.2+）：启用虚拟线程后，单进程可以轻松处理数万并发，但 CPU 密集计算仍是单核瓶颈，最终还是需要多实例

如果你用 Python asyncio：

- 单进程事件循环能处理大量 I/O 并发，但受 GIL 限制只能用单核 CPU
- 生产环境通常用 `Gunicorn + 多 worker 进程`，每个 worker 运行独立的 asyncio 事件循环，配合 Nginx 负载均衡

总结：

**单进程在 I/O 密集型场景下可以扛很高的并发量**（尤其是异步/协程模型），但**在 CPU 密集型场景下单进程必然不够用**，因为一个进程最多用一个 CPU 核心。高并发服务最终都需要多进程/多实例来利用多核，再配合负载均衡实现横向扩展。这个结论与语言无关，是操作系统的基本约束。
